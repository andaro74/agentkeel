# M06 — A team can do this in a day

## In one sentence

One developer creates an agent from the template and ships it in a day,
without touching the safety pipeline.

## Why it matters

Until now every agent on this platform was built inside the platform's
own project, by the person who built the platform. A team that wants an
agent of its own needs a starting point, and the rules have to follow the
agent into the team's project: who owns each decision, which tests it
must bring, and which checks it cannot switch off.

Two kinds of developer are the risk. One forgets: leaves an owner's seat
empty, ships no tests. The other cheats: deletes the check from their own
project, or adds a fake check that always says yes. M06 is meant to show
that neither gets an agent out, and that an honest developer still ships
within a working day.

One person holds every owner's seat on this project. The developer who is
timed is that same person, on a clean computer and a second account that
can write to the agent's project and change nothing about its rules.

## What we planted

We wrote five ways for the claim to be false and put them in the
repository before any code that could catch them.

Two are a new agent's first change with something missing. In the first,
nobody is named for any of the seven owner's seats. In the second, the
seats are filled but the agent brings no tests. Today both would pass
every check the platform runs.

The third is a cheat: a change in the agent's project that adds a fake
job with the same name as the platform's check, one that always says yes,
to a change the real check would refuse. Today the platform's own project
could not tell the fake from the real one, because it asks for its checks
by name.

The fourth is the stopwatch. The second account creates nothing and
changes no rules; it follows the quickstart from the moment the agent's
project exists to the moment the agent answers and appears in the list of
agents. One working day is eight hours by the clock, breaks included.

The fifth is the list itself: a dashboard panel that shows an agent the
platform has never heard of, because its query reads a second source.

## What happened

**Red.** The template, the platform's check, the list of agents and its
dashboard panel were built and are running. The claim was not measured.
No developer shipped an agent from the template, because the platform's
check refused every change in every agent's project, a correct one too.
Two of the three planned tries were made; the timed one was not.

| What was tried | Result |
|---|---|
| The owner's own test: a new agent's first change, with no owners named and no tests | refused by the platform's check at 14:24 on 1 October, for both planted reasons and for a third. The check could not read one field of the project's protection rules. GitHub shows that field only to an app allowed to change the rules, and the platform's app asks for read access only. A missing field is treated as a weakened rule, so every change in every agent's project is refused. The test stopped there: nothing was merged, deployed or listed |
| The cheat: a fake check with the platform's check's name, made by the second account | not mergeable. The fake said yes at 15:23. The platform's check said no at 15:24. GitHub asks for the platform's check from the app that posts it, so the fake did not count. The platform's check would have said no to any change at that point, so this shows that a fake does not count. It does not show the check catching this cheat for this cheat's own fault |
| The stopwatch: the second account ships an agent within eight hours | not tried. The second account has one clean first attempt. Product kept it for M07, after the fix, rather than spend it on a check that refuses everything |
| The dashboard against the list of agents | the panel lists refagent, and the list holds refagent and nothing else. Nothing on the panel is missing from the list |

In the tests, the two forgetful changes (no owners, no tests) and a panel
reading a second source are each refused for their planted reason.

We wrote down before the run what the record would say about the cheat.
Read without a key, from outside the agent's project, GitHub calls that
change "unstable", which can mean it may merge. We said the run would read
the same, because its key has no rights in the agent's project. The run
read "blocked". Our statement was wrong. What GitHub says about a change
depends on whose key asks, and the record keeps the verdict but not the
answer GitHub gave or the key it gave it to. Both are M07's to fix.

The fix for the refusal is to let the platform's app change protection
rules, so it can read them. That is a decision for Security, because an
app that can change the rules could also loosen them. It is M07's, with
the timed run.

**What red does not mean.** It does not mean a forgetful or a cheating
change got through: none was merged. It means the day was never timed,
so nobody knows yet whether a team ships in a day. It also does not mean
the template works. The owner's own test never got past its first
change. When the timed run happens, it counts the agent's answer to one
of its own tests as done if either of its two tests passes. With one
yes-or-no answer, a guess passes one of two about half the time.

The row is red because the recorded results say so, not because someone
wrote it here.

## For the business user

What M06 is meant to show: a team can start an agent from the template
and ship it within a working day, with every owner named and its own tests
in place, and it cannot skip the platform's checks by editing its own
project. Security owns the check and the list of agents; the threshold
owner owns the eight hours.

Not measured at M06, stated now. The developer timed is the author, not a
stranger to the platform. A second person could still write a ruling in
an owner's name, because a ruling is a file and the owner is a line in
it. The platform's own project still asks for its checks by name; only
agent projects get the bound check. The agent's knowledge base, a way to
mark a flaky test, and three of the four developer guides move to M07.
So do the timed run, the two recordings of the platform at work (Acts 1
and 2), and the fix that lets the platform's check read an agent's rules.
