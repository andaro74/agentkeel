# M00 — Start from nothing

## In one sentence

Before any guardrail, a plain model gets the trick questions wrong; every
later number is measured against that.

## Why it matters

A score means nothing alone. "The agent got 14 of 15 right" sounds good
until someone asks what a cheap model with no data and no rules would
have scored on the same questions. M00 answers that first, and then does
not touch the answer again. It stops no attacker by itself; none of the
threats in the platform's list is answered here. It is the control: the
thing that lets every later milestone say "this is how much better, and
here is what it is better than."

## What we planted

We wrote fifteen questions about a made-up film slate: can we publish
this title, in this country, on this service, on this date. Nine are
ordinary. Three are traps, where the obvious answer is wrong: a cinema
date moved but the home-rental date did not; a licence that lets us
publish but is not ours alone; a sequel that does not come with the
rights to the first film. Three ask for things the agent must never
give: the plot of an unreleased film, an actor's agent's phone number, a
deal summary for a competitor.

Then we pointed the cheapest model we could find at all fifteen, with one
instruction and nothing else. No rights table, no contracts, no filter.
We expect it to get the traps wrong, bar luck. On our own trial run it
missed two of the three and got the third right for the wrong reason;
we wrote that down as a finding about the question and changed nothing.
Nothing exists yet to stop the three forbidden requests.

We will also try to file a result that has no baseline attached. It
should be refused.

## What happened

The cheap model answered all fifteen questions with no table and no
rules. It got one right.

| | Score |
|---|---|
| Traps | 1 of 3 |
| Ordinary questions | 0 of 9 |
| Forbidden requests refused | 0 of 3 |
| Questions that have never been answered right | 14 of 15 |

The one it got right is a trap, and it got it right for the wrong
reason: it called the sequel unavailable because it read the date wrong,
not because it knew the rights do not carry over. That is written down as
a finding about the question, not fixed.

It has been asked the same fifteen questions five times now, with the
same model, the same instruction and the same settings. It has never
given the same set of answers twice. On the first run in the build
pipeline it also got one ordinary question right; on this one it got
none. The trap it gets right is the same trap every time. Three of the
fifteen have been answered correctly on some run; no run has ever got
more than two right; the run this milestone rests on got one.

The thing we tried to sneak past the check was refused. A result filed
with no baseline attached is rejected, and the pipeline recorded that it
was rejected there and not only on a laptop. The second check also
passed: a change that reached the main branch with no signed decision
behind it was blocked and never merged, and that check is now required.
It is not yet proof that nobody can switch the check off — the repository
owner still can, and we cannot read from the outside whether they have.
That gap is written down and dated.

**The result is GREEN.** GREEN means nothing regressed against an empty
history; it does not mean 2 of 15 passing is good. It means the control
is now written down, in a file nobody can edit after today, and every
number this project reports from here is measured against it.

### What we found on the way

- **The plain model passed one of our traps.** We left the trap alone and
  wrote down why it passed. Changing a question because the answer
  embarrassed us is how a score stops meaning anything.
- **The same model, asked the same question twice, does not give the same
  answer.** Not sometimes — five runs, five different sets of answers,
  with the setting that is supposed to make it repeat itself. Two of
  those runs print an identical scoreline and still disagree on four of
  the fifteen answers underneath it. The floor we measure against moves.
  We know by how much, and it is written down.
- **The pipeline's own credentials were wider than the job needed.** It
  could reach six models; the job uses one. Narrowed to one model and to
  the single file that runs the evaluation, and then used once, by this
  milestone's own last run — so it is a thing that has happened, not a
  thing we wrote down. One run is all the evidence it has.

## For the engineer

| | |
|---|---|
| Read | `evals/goldens/v1/g-001.yaml` to `g-015.yaml`; `src/baseline/` (the control: one prompt, Converse, temperature 0); `scripts/seed_slate.py` and what it writes under `data/`; `milestones/M00/feasibility.md` |
| Run | `make validate`, then `make evals-local` (your credentials, your cost, writes `evals/local/` only, not evidence) |
| The check | `src/verdict/`: the runner writes raw answers, `build.py` alone writes the result file, `gate.py` alone reads it. On the seeded file with no baseline attached, `gate.py` exits 2, REJECTED, `'baseline_card_ref' is a required property`. The envelope field that records it holding in CI is `checks.F0_2`. |
| The freeze | ADR-0002 and `tests/test_baseline_frozen.py`: four files, four hashes, and a diff against tag `m00`. Edit the prompt by one byte and `pytest` fails. |
| Reuse | Write your traps and your naive control before your agent. Keep the control out of reach of the questions' data. Never improve it. |

## For the business user

When a team creates an agent on this platform, its scorecard will always
show two columns: their agent, and the plain model on the same questions.
A team cannot make its agent look better by quietly making the comparison
weaker; the comparison is fixed at this milestone and the person who owns
the questions is not the person who builds the agent. If the plain model
ever starts passing a trap, that is written down as a finding about the
trap, not fixed on the quiet.
