# M04 — Changing the model is tested, or it's blocked

## In one sentence

When a team switches the agent to a different model, the switch is
tested on its own proposal before it can go in; if a test that used to
pass now fails, or answers get much slower, it can't go in.

## Why it matters

The model under an agent changes more often than the agent does. A
provider releases a new version, retires an old one, or a team wants a
cheaper one. A new model can pass the obvious questions and still break
the one habit the agent depends on: here, looking the answer up in the
rights table instead of guessing it. It can also be slower, or use more
tokens, while every answer stays right. And a model can be retired under
an agent that nobody is watching.

M04 is about the switch. The switch is a proposal that changes one line,
the model the agent is pinned to, and the full test run measures that
proposal before it can merge. For the result to mean anything, the tests
must give the same answers when nothing changed. So M04 runs the same
model twice and requires the two runs to agree.

One person holds every owner's seat on this project. The person who
names which model is "equivalent" also decides how much slower is too
slow. The platform records who ruled. It does not record that a second
person looked.

## What we planted

We wrote five ways for the claim to be false and put them in the
repository before any code that could catch them.

The first is a breaking switch: the agent pinned to a much smaller
model, and a run in which every answer is right and cites a real row
and clause, but none of them came from the rights table. The model
printed its lookup as text instead of making it, or made it with
arguments the lookup refuses. Today the platform checks what the answer
says, not where it came from, so every answer passes and the switch
looks safe.

The second is a switch to the model we named as equivalent, a sibling of
the one the agent runs today. Today the account's permissions let the
test run call only two models. The switch would fail every question for
a reason that has nothing to do with the model, and the team would read
it as "the new model is broken".

The third is two runs of the same model on the same code that disagree
on one question. Today nothing compares two runs, so a flaky question
would show up later as a failure blamed on some unrelated change.

The fourth is a run where every answer is right, but three times as
slow as today's model, and a second run that uses twice the tokens.
Today nothing reads either number against the model it replaces.

The fifth is the agent pinned to a model its provider has scheduled for
retirement on 14 October 2026, with that date written in. Today the
check that runs on every change does not read the date.

## What happened

**Red.** The breaking switch went red for the right reason, and the same
model run twice gave the same answers. But the switch we named
equivalent before any run went red too: it got one question wrong that
today's model gets right. That makes the claim false, and the row says
so.

| | Result |
|---|---|
| Answers that look right but never came from the rights table | refused: an answer now passes only when the lookup was actually made and returned the row the answer cites |
| The equivalent model blocked by the account's permissions | refused: the test run may now call each candidate model, and the equivalent one answered every question |
| Two runs of the same model that disagree | refused: when the model changes, or on request, the agent runs twice in one job, and any question whose result differs makes the result red |
| An answer three times slower, or twice the tokens, than today's model | refused: the result goes red when the slowest answers are over 2 times, or the tokens over 1.5 times, today's model in the same setting |
| A model pinned 17 days before its retirement date | refused by the repository's checks: 30 days or fewer is a failure |
| Today's model, the same model run twice | 9 of 9 ordinary questions and 2 of 2 traps, each answer looked up; both runs agreed on every question (the measuring pull request's result; 97,635 tokens of 150,000 for the whole test job, today's model and the plain control each run twice). The plain control's two runs disagreed on one question; that is reported, not counted |
| The breaking switch (Llama 3.1 8B), pull request #25 | red: 0 of 9 ordinary questions and 0 of 2 traps; 11 questions that passed before now fail. Both runs agreed. Not refused, not blocked by permissions, not over the token limit |
| The equivalent switch (Claude Sonnet 4.5), pull request #26 | red: 8 of 9 ordinary questions and 2 of 2 traps; one question, `g-005`, passed before and fails now, in both of its runs, on its first pull request run and again after the repairs |

The question it gets wrong is about a release window. The contract's
embargo is in São Paulo time; at 01:30 UTC on 14 May it is still 13 May
there, so the title is not yet available. Today's model says so. The
equivalent model says it is available, and cites the right row and
clause. The rule was written before any run: if the model named
equivalent loses a question, the claim is false and the label is not
moved to fit.

It took three pull requests to read the two switches. The switches were
opened after the second one merged, and on both of them the test suite
itself failed: nine and ten of its tests assumed today's model was the
pinned one. The review of the second pull request had not caught that;
the switches did. The third pull request repaired the tests and added
the part of the gate that reads each switch's own result. The reviews
of that pull request found twice that a switch's branch could slip its
own code into the reading, and it was closed off before it merged. The
switches' results are recorded beside every run's result and printed
in the row; they block no pull request. Anyone who can push to a
switch's branch can still write its result by hand; closing that is
M05's. Blocking on them would have made
every pull request red, since the equivalent switch had already failed.

**What red does not mean.** It does not mean the gate missed anything:
both switches were caught, and neither is merged. On their first runs both were also red for a reason of the test suite's own, which assumed today's model; the re-runs, after the repair, have every other check green, so their red is the model's. It means one of the
two models we expected to pass did not. Nothing here watches the
provider for new models or retirement dates, and nothing grades answers
by meaning; both arrive at M07. The equivalent switch ran in the test
runner, not in the deployed agent. The slowness and token limits were
never crossed by a real run, only by the planted ones. And one person
holds every owner's seat.

The row is red because the recorded results say so, not because someone
wrote it here.

## For the business user

What M04 is meant to show: when a team moves its agent to a different
model, the proposal is tested like any other change, and it cannot go in
if an answer the agent used to get right is now wrong, if the agent
stops looking answers up, or if answers get much slower or costlier. A
model named equivalent must pass, or the claim is false. The threshold
owner names which models are candidates and how much slower is too
slow; the data owner decides what counts as a correct answer.

Not measured at M04, stated now. Nothing watches the provider for new
models or retirement dates yet, and nothing tries a new model on its
own; that arrives at M07. The grader model arrives at M07 too; until
then "correct" means the answer's fields match and came from the rights
table, compared by code. The equivalent switch was to be shown mergeable, not
merged; at the close it was not mergeable (see What happened). Whether a model can be called without the agent's guardrail is
M05's.
