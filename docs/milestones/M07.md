# M07 — Upgrades come to you

## In one sentence

A new platform version, a new model, or a retirement arrives as a PR; the
team never edits the pipeline.

## Why it matters

An agent is not finished when it ships. The platform under it changes,
the model it runs on is replaced or switched off by its maker, and one
day the agent itself should be turned off. If each of those depends on a
team remembering to do something, some teams will not, and the platform
ends up with agents on old rules, on models that are about to disappear,
or still answering long after anyone owned them.

So the change should come to the team, as a proposal they can read and
accept, tested by the same checks as any other change. And a change that
turns out wrong should be reversible: putting the old version back must
really put it back.

There is one thing to do first. At the last milestone no team could ship
an agent at all, because the platform's own check refused every change in
every agent's project. An upgrade needs an agent to upgrade. So this
milestone starts by fixing that check, and by timing a developer shipping
an agent in a day, which the last milestone could not do.

## What we planted

We wrote six ways for the claim to be false and put them in the
repository before any code that could catch them.

The first is the fix itself. Today the platform's check refuses every
change in every agent's project, so there is no agent. To read the
project's protection rules, the platform's app needs a stronger
permission, one that would also let it loosen those rules. So we planted
what must be true before it gets that permission: its key may only be
used for one project at a time, and something must read back exactly
what the app is allowed to do and where its key can be used, and refuse
anything nobody approved.

The second is a new platform version. Today nothing tells a team a new
version exists; someone would edit the agent's files by hand.

The third is turning an agent off. Today nothing does: an agent whose
project was abandoned would keep answering. No team's agent has run yet,
so this is what the code would do, not something we have seen.

The fourth is undoing a model change. Today, if a team switched models
and then switched back, nothing checks that the agent is really running
the old version again.

The fifth and sixth are about the dashboard. One is a panel rigged to
show green for a run that was red. The other is a check that quietly
stops checking, with nobody counting.

## For the business user

What M07 is meant to show: a team with an agent on the platform does not
have to watch for new versions, new models or end-of-life dates. Each
arrives as a proposal in the team's own project, with the reason, and
goes through the same checks as the team's own changes. The owners named
on the agent decide whether to accept it. Security owns what the
platform's app is allowed to do; the threshold owner names which model is
a candidate.

Not measured at M07, stated now. A person still names the candidate
model; the platform opens the proposal. An agent is turned off when its
owners accept the proposal to retire it; nothing turns off an agent whose
project is simply deleted. Several things planned for this platform are
not built at all, and the platform's documents now say so: the agent's
knowledge base, a second model that grades answers, a mirror of results
in a third-party tool, a human approval step as a shared tool, and two of
the four dashboard panels. The dashboard is read through its data, not
through a browser, so nothing checks what a person sees on the screen.
