# M07 — Upgrades come to you

## In one sentence

A new platform version, a new model, or a retirement arrives as a PR; the
team never edits the pipeline.

## Why it matters

An agent is not finished when it ships. The platform under it changes,
the model it runs on is replaced or switched off by its maker, and one
day the agent itself should be turned off. If each of those depends on a
team remembering to do something, some teams will not, and the platform
ends up with agents on old rules, on models that are about to disappear,
or still answering long after anyone owned them.

So the change should come to the team, as a proposal they can read and
accept, tested by the same checks as any other change. And a change that
turns out wrong should be reversible: putting the old version back must
really put it back.

There is one thing to do first. At the last milestone no team could ship
an agent at all, because the platform's own check refused every change in
every agent's project. An upgrade needs an agent to upgrade. So this
milestone starts by fixing that check, and by timing a developer shipping
an agent in a day, which the last milestone could not do.

## What we planted

We wrote six ways for the claim to be false and put them in the
repository before any code that could catch them.

The first is the fix itself. Today the platform's check refuses every
change in every agent's project, so there is no agent. To read the
project's protection rules, the platform's app needs a stronger
permission, one that would also let it loosen those rules. So we planted
what must be true before it gets that permission: its key may only be
used for one project at a time, and something must read back exactly
what the app is allowed to do and where its key can be used, and refuse
anything nobody approved.

The second is a new platform version. Today nothing tells a team a new
version exists; someone would edit the agent's files by hand.

The third is turning an agent off. Today nothing does: an agent whose
project was abandoned would keep answering. No team's agent has run yet,
so this is what the code would do, not something we have seen.

The fourth is undoing a model change. Today, if a team switched models
and then switched back, nothing checks that the agent is really running
the old version again.

The fifth and sixth are about the dashboard. One is a panel rigged to
show green for a run that was red. The other is a check that quietly
stops checking, with nobody counting.

## What happened

**Red.** Two of the three kinds of change arrived the way this page
says, and one did not. A new platform version and a retirement each came
to the team as a proposal the platform opened, each time after the owner
started the platform's job by hand, and each went through. The new model
was proposed the same way, for the platform's own reference agent, and
then failed one of that agent's tests, so it was not accepted. Before any
of that, the first agent a team shipped took almost nine hours to deploy,
against a limit of one hour, because of faults in the platform's own
deployment. And the
milestone took five rounds of changes where four are allowed.

The count is two of three.

We wrote down, before each try, what the record would say. Three of our
sentences were wrong. The one that changed a result: we expected the
stopwatch run's first change to be refused for the planted reasons, and
it was refused for a typing mistake instead. One number was off by four
seconds. And one sentence, written after the last try, said everything
had gone as stated when the owner had started the platform's jobs by
hand more often than the plan allowed. Each was left as written, with the
correction beside it.

Three fixes were made to live systems during the tries, by hand, before
anyone had formally approved them: two permissions for the role the
platform creates agents with, and a correction to who may write the
observer's records.
They are written down as that, and put to the security owner afterwards.

The screen recording of the stopwatch run was not made. A short film
made afterwards reads the run back from its records; it is not a
recording of the run.

**What red does not mean.** It does not mean an upgrade needed someone
to edit the pipeline. The two that went through needed none. The model
change was never accepted, so this was not tested for it. It does not
mean the retired agent kept answering, or that undoing a change left the
new version running. It means the first agent took almost nine hours
where one was promised, the one model on offer did not pass the
reference agent's tests, and the work took a round more than the rule
allows. It also does not mean the cheaper model is bad: it failed one
test of this agent, on the one proposal that measured it.

**What the passes do not mean.** One hour is one developer, once, who is
also the platform's author, with the owner starting the check by hand.
The 139, 144, 51 and 368 seconds are what the platform took once the
owner started it; what its own timers take was not measured. One person
holds every owner's seat, the security owner's too: "the owners accepted
it" means that person did, and no second person looked. "Noticed, not
prevented" means a project can be left without its check for as long as
nobody pushes a change. A retired agent's computer resources are not all
gone: two network connections were still there four and a half hours
later.

The row is red because the recorded results say so, not because someone
wrote it here.

## For the business user

What M07 is meant to show: a team with an agent on the platform does not
have to watch for new versions, new models or end-of-life dates. A new
platform version and a retirement arrive as proposals in the team's own
project, with the reason, and go through the same checks as the team's
own changes. A new model is proposed only for the platform's reference
agent; a team's agent keeps the model it names. The owners named
on the agent decide whether to accept it. Security owns what the
platform's app is allowed to do; the threshold owner names which model is
a candidate.

Not measured at M07, stated now. A person still names the candidate
model; the platform opens the proposal. An agent is turned off when its
owners accept the proposal to retire it; nothing turns off an agent whose
project is simply deleted. Several things planned for this platform are
not built at all, and the platform's documents now say so: the agent's
knowledge base, a second model that grades answers, a mirror of results
in a third-party tool, a human approval step as a shared tool, and two of
the four dashboard panels. The dashboard is read through its data, not
through a browser, so nothing checks what a person sees on the screen.
