# M02 — Rules have owners

## In one sentence

A rule, a test, or a threshold changes only when the person who owns it
says so, and loosening one needs two owners.

## Why it matters

The quickest way to make a red build green is not to fix the agent. It
is to raise the bar it failed, soften the test it failed, or delete the
test. Each of those is one line in one file, and each looks like
housekeeping in a code review. M02 is to give every file in the platform
an owner, and to make the platform refuse a change to an owned file
unless a written ruling from that owner comes with it. Loosening anything
is to take two owners. And the person who runs the repository is not to
get past a red check either: the repository is already set so that
nobody can, and from this milestone the platform is to check that setting
every time. The checks were built in the second pull request, and there they refused
four of the five planted cases in a copy of the repository: the loosened
limit with one owner and with two papers from one owner, the softened
question, the one-ended connection, and the renamed question. After that
pull request merged the checks were switched on, the five cases were
opened as real pull requests, the owner tried the override, and the third
pull request read what happened. What happened is below.

One thing to say plainly before the rest. On this project one person
holds every owner's seat. "Two owners" here means two written rulings
from two seats, and one person can write both. What the platform holds
is that the change is named, under the seat that owns the file, in a
file that stays with the history. It does not hold that somebody else
agreed. That is the design for a proof of concept with one engineer; a
team would put a person in each seat.

## What we planted

We wrote five changes that must never reach the main branch, and put
each one in the repository as a patch a test can apply.

The first raises the spending limit on a test run from 150,000 tokens to
300,000, with a ruling from the one owner who sets that limit and nobody
else. One owner is not enough to loosen a limit. A second version of it
comes with two rulings, both from the same owner; two pieces of paper
from one seat are still one key.

The second edits a trick question so that the wrong answer now counts as
right: the question was written to catch an agent that ignores a
holdback date, and the edit tells the grader to reward exactly that.

The third has the reference agent declare that it may call a second
agent, while the second agent says nothing about being called. Every
connection between agents must be declared on both ends.

The fourth is not a file but an attempt. After the checks are in place,
the owner of the repository will try to merge a change whose check is
red, using the administrator's override; and then will try to give
themselves permission to override, and see whether the platform notices.

The fifth renames a test question's id, keeping its content. A question
is retired, never renamed: renaming one erases its history.

## What happened

**Green.** Every change we planted was refused on a real pull request,
the owner could not get past a red check, and the one change that came
with two owners' rulings went through.

| | Result |
|---|---|
| The loosened limit with one owner's ruling (pull request 14) | refused: a loosening needs two owners |
| The same loosening with two papers from one owner (15) | refused: two papers from one seat are one key |
| The softened trick question (16) | refused: no ruling, and a loosening of a test |
| The one-ended connection between two agents (17) | refused: both ends must declare it |
| The renamed test question (18) | refused: a question is retired, never renamed |
| The owner forcing the merge of pull request 14 past its red check | refused by the repository itself, and the refusal is in its own record |
| The owner giving themself the right to force merges | the platform's check went red while the right was listed, and stayed red until it was removed |
| A trick question retired with two owners' rulings (pull request 12) | merged |
| The agent's answers, now running inside the wrapper | 9 of 9 ordinary questions; 2 of 3 traps; 0 of 3 forbidden requests refused |

The trap count fell from 3 of 3 to 2 of 3 because one trap was retired
in this milestone, for a reason found at the start of the project: the
plain model was getting it right by luck, so it measured nothing. Its
replacement has never been answered right by any agent, and a question
that has never been answered right is never a reason to go red. The
forbidden requests wait for the guardrail that arrives in M03.

**What green does not mean.** Green means each planted change was
refused and the two-owner change was merged; it does not mean a second
person looked, because on this project one person holds every owner's
seat and writes both rulings. It does not mean the checks cannot be
switched off: until M05 they are run by the pull request's own code, and
the same person who owns the pipeline is the one who would have to
notice. And one of the platform's limits refused a call once, by
accident rather than on a case we planted, so nothing here calls it
working.

The result is green because the gate said so, from the repository's
record of five real pull requests and two real attempts, not because
someone wrote it here.

## For the business user

What M02 shows: when a team runs an agent on this platform, the tests it
must pass, the limits it must stay under and the rules it must follow
each have a named owner, and none of them can be changed on the quiet. A
change comes with a ruling from its owner, kept with the history.
Loosening a test or a limit needs two. The team decides what the agent
says; the owners decide what counts as passing; nobody, including the
person who runs the repository, merged past a red check when they tried.
Each check has refused its planted case on a real pull request; the
limit below still stands.

One limit, stated now. At this milestone one person holds every seat, so
"two owners" is two rulings that one person can write. The platform
records that the change was named and by whom; it does not record that
a second person looked.
